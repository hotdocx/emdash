## Outcome And Corrected Priority

No from-scratch backend redesign is indicated. The current backend-neutral
Core, generic outer LF, checker/evaluator, catalog-owned categorical
computation, generic transfer engines, and Lambdapi conformance boundary are
retained.

The highest-impact missing architecture is instead the frontend that turns an
ergonomic TypeScript expression with categorical binders and convenient
applications into explicit active emdash owners. The immediate work therefore
has two product-facing outcomes:

1. package the existing dependent Sigma-telescope computation as a runnable,
   readable TypeScript demo; and
2. implement and qualify categorical bracket abstraction and type-directed
   application, first for ordinary functors and then for one
   natural/displayed dependent example.

The demo does not depend on transcribing the measured remaining 70 root
commands or the two 58/25-command extension closures. Those transfers expand
library coverage and remain useful future scale evidence; they do not create
the first functioning dependent end-user path.

The final frontend design must not be called settled merely because the
backend accepts explicit Core. It becomes provisionally settled only after
the ordinary functorial slice and one natural/displayed Pi/Sigma slice pass
end to end without owner-specific checker or evaluator shortcuts.

## Acquisition And Direct Transfer Decision

### Canonical declaration parsing is deferred

The paused experiment attempted only canonical `symbol` declarations and
explicitly excluded runtime rules, proof patterns, inductives, tactics, and
notation. It had already reached 1,022 source lines before dedicated tests and
was neither exported nor consumed. USABILITY-0A removes that isolated
untracked experiment.

The following completed work is independent and must be preserved:

- exact public/protected/private compiled module exposition;
- checked tactic-source retention as an opaque theorem boundary;
- exact source/export/import/hash acquisition contracts;
- measured source-prior closure and dependency inventory for
  SCALE-STRESS-3B; and
- the generic transfer engines through which a future direct or generated
  specification is compiled.

No architectural rule prohibits a future narrow parser or generator. It may
be reconsidered only after a measured repetitive transfer tranche shows that
such an adapter costs less than direct typed construction. Its output must
still feed the same IR and policy boundary, fail closed, remain reproducible,
and stay outside the trusted checker/evaluator.

### Direct typed transfer remains feasible and default

A Codex agent can construct the remaining typed transfer IR in bounded
tranches. A parser is not required. Per-command cost is nonuniform:

- an opaque signature is often roughly 10–40 lines plus linkage and tests;
- a straightforward transparent definition is often 20–100 lines;
- a runtime rule adds typed captures, patterns, subject-reduction evidence,
  positive cases, and near misses;
- a proof-time rule also adds variables, ordered constraints, and execution
  tests;
- an inductive adds generated owner/signature/computation boundaries; and
- a tactic theorem requires an explicit checked-source/opaque policy.

The measured “70 + 83 declarations” therefore is not 153 uniform headers.
The root prerequisite alone contains two inductives, many explicit theorem
bodies, two tactic bodies, protected visibility, and generated-owner
boundaries. Direct transfer remains feasible, but likely costs several
thousand lines plus review and differential testing.

For this project, “mechanical transfer” means that another already-qualified
mechanism is added through typed data, linkage, authority policy, and focused
evidence—not that every `.lp` term is automatically parsed. Small builder
helpers and command-specific checked extraction are encouraged when actual
repetition appears. A new checker/evaluator algorithm, owner-named shortcut,
or silently opaque unsupported term is not mechanical.

## The Outer-LF Versus Categorical-Binder Boundary

An outer LF abstraction such as an ordinary dependent function:

```text
λ x : A. t
```

is represented by `KernelLambda` and eliminated by ordinary LF application.
That remains correct and necessary.

A categorical abstraction:

```text
h = λ x :^f A. F[x]
```

has a different target. It must elaborate to an actual object
`h : Functor A B` (using the active source convention for that judgment), not
merely to an LF function from `τ(Obj A)`. In the eta case it can compile
directly to `F`.

The frontend may expose one convenient application form, but elaboration must
choose an explicit eliminator from classifier, argument dimension, expected
type, polarity, and displayed context. For the ordinary eta example:

```text
h[y]  ↦ fapp0 h y
      ↦ fapp0 F y
```

when `y : Obj A`, while:

```text
h[p]  ↦ fapp1_fapp0 h p
      ↦ fapp1_fapp0 F p
```

when `p : Hom A x y`.

The exact capped arrow-action owner is `fapp1_fapp0`.
`fapp1_func F x y` denotes the whole hom functor and is selected when the
expected result is that complete action rather than its value on one arrow.

The same application-classification family includes:

| Classifier and expected shape | Explicit target family |
| --- | --- |
| outer LF Π | ordinary Core call |
| functor, object argument | `fapp0` |
| functor, whole hom action expected | `fapp1_func` |
| functor, one arrow argument | `fapp1_fapp0` |
| transfor, point evaluator expected | `tapp0_func` |
| transfor, point value expected | `tapp0_fapp0` |
| transfor, full off-diagonal action expected | `tapp1_func` |
| transfor, one off-diagonal value expected | `tapp1_fapp0` |
| displayed functor/transfor | the corresponding active `fdapp*`/`tdapp*` owner |
| dependent section/Pi | `piapp0` or the corresponding active `piapp1_*` owner |

USABILITY-1A must turn this table into precise synthesis/checking judgments
against current owner signatures. Unsupported or ambiguous selection fails
with the inferred classifier, argument dimension, expected type, and candidate
owners; it never guesses.

## Contextual/Wiring IR And Bracket Abstraction

Active v3.2 already contains much of the ordinary categorical combinator basis
needed for an implementable compiler:

- product evaluation and higher action (`Eval_func`);
- product maps and pairing;
- curry and uncurry;
- functor composition;
- weakening through `Const_func_func`;
- exchange through `sym_func_func`; and
- contraction through `diag_func_func`.

The frontend will use a small first-order contextual/wiring IR between the
ergonomic surface and explicit Core. It records, at minimum:

- ordered categorical input slots and their classifiers;
- each subterm's free-slot usage;
- inferred result classifier and cell level;
- polarity/variance transformations;
- duplication, discard, and permutation requirements;
- application/evaluation edges; and
- source provenance for diagnostics.

A typed categorical bracket-abstraction pass then lowers:

- an unused variable to weakening/a constant functor;
- the variable itself to identity;
- reordered variables through symmetry;
- repeated variables through diagonal/contraction;
- an application through evaluation after typed pairing;
- composition through functor composition;
- a nested abstraction through curry; and
- multiple inputs through the active product/context construction.

A DAG or string-diagram representation may later improve sharing,
visualization, or diagnostics, but it is not required for the first slice.
Graph sharing is an implementation optimization; categorical contraction is
a semantic duplication of input and must remain explicit.

The existing `src/v3_2/structural.ts` transformations are meta-level dependent
telescope maps used by source scoping. They are not the internal categorical
weakening/exchange/contraction owners and must not be silently reused as if
they were.

## Binder Information Uses Orthogonal Axes

The frontend must not create a distinct binder mode from every
`fapp*_func`, `tapp*_func`, or related owner. Those owners chiefly encode
elimination dimension and packaging.

The design tracks at least these orthogonal axes:

| Axis | Initial values and interpretation |
| --- | --- |
| plicity | explicit or implicit |
| variation capability | functorial, natural/indexed, or object-only |
| polarity | covariant or contravariant, represented through `Op_cat` and the active `z^-` convention where applicable |
| classifier/cell level | object, arrow, transfor, or higher cell; normally inferred |
| dependency | ordinary or displayed/context-indexed; primarily carried by the classifier/context rather than a flat enum |

Object-only is not synonymous with groupoidal. An object-only variable has no
arrow action. A variable ranging in a groupoidal category can still vary
functorially along invertible arrows. Groupoidality is a property of the
classifier, not the meaning of a `:^o` annotation.

Similarly, `fapp1_func`, `tapp0_func`, and `tapp1_func` are full action or
evaluation functors. They are not evidence for three new source binder modes.

The canonical source already settles `:^n` while leaving additional
functorial/object-only source annotations open. USABILITY-1A may choose an
internal TypeScript representation without prematurely standardizing final
Lambdapi notation.

## Reuse From The Older TypeScript Prototype

The `main` worktree's old prototype is implementation evidence, not v3.2
category-theory authority. Useful generic pieces include:

- HOAS-like λ/Π construction;
- binder-mode metadata;
- explicit object/arrow/transfor/displayed action nodes;
- bidirectional elaboration, holes, metavariables, and unification; and
- explicit functor construction with computational coherence checking.

Its mode-aware lambda elaboration nevertheless rebuilt an LF lambda/Π and
validated metadata. It did not compile a functorial lambda automatically to
the active v3.2 categorical structural combinators. The new
bracket-abstraction layer is therefore real new frontend work.

HOAS versus de Bruijn is not the architectural decision. The supported
TypeScript API may remain ergonomic HOAS/PHOAS while immediately replacing
the callback token by a first-order locally nameless node. Stored Core and
transfer artifacts remain immutable and name-independent.

Reusable generic algorithms may be ported or cleanly reimplemented. The old
mutable global rule arrays, stale category-specific AST, named-HOAS storage,
retired D0/D1 compatibility API, and fail-soft behavior must not return.

## Natural And Displayed Staging

The first natural/displayed slice must use only actions already justified by
active owners, initially including:

- `Functord_cat`;
- `Sigma_cat`;
- `Pi_cat`;
- `piapp0` and the applicable `piapp1_*` owners; and
- active displayed functor/transfor projection or internalization owners.

If a candidate needs a missing general displayed contraction, reindexing, or
coherence owner, elaboration fails with a precise
`unsupported-categorical-action` diagnostic. That evidence opens the
smallest focused Lambdapi owner-position proposal under the nested SOP; it
does not authorize inventing a TypeScript-only rule.

This fail-closed boundary lets the compiler architecture stabilize while
mathematical coverage grows incrementally. The later groupoidal
specialization/closure of the existing directed categorical DTT remains a
separate Lambdapi-first development and is not conflated with object-only
frontend variables.

## USABILITY-1A Completion Record

USABILITY-1A is specified by
[`TYPESCRIPT_ELABORATOR_V3_2_CATEGORICAL_BINDER_RFC.md`](./TYPESCRIPT_ELABORATOR_V3_2_CATEGORICAL_BINDER_RFC.md)
and the root-only executable artifact
`src/v3_2/categorical_surface_spec.ts`.

The RFC settles the next compiler boundary:

- outer dependent-LF abstraction remains `KernelLambda` checked against an LF
  Pi and eliminated by ordinary Core call;
- categorical abstraction is a separate judgment compiled through a typed
  contextual/wiring IR to an actual ordinary or displayed categorical
  object;
- plicity, variation capability, polarity, cell level, and
  ordinary/displayed dependency are orthogonal axes;
- an ergonomic callback is immediately reified into first-order locally
  nameless storage with ordered context, free-slot usage, result classifier,
  polarity, dependency, cell level, and source provenance;
- classifier, subject form, argument dimension, expected action shape, and
  dependency select one explicit semantic owner; and
- a whole action request is distinct from applying an action to one value, so
  a concrete transfor is never erased merely to obtain an evaluator.

The executable specification freezes sixteen application judgments. The
eligible existing paths are outer LF call, ordinary functor object/full
hom/capped hom action, ordinary transfor full point evaluator/capped point
component, and reviewed dependent-section object evaluation. It separately
records:

- ordinary off-diagonal transfor action as representable in explicit Core but
  blocked by the active kernel's external-naturality reservation;
- full and capped section arrow action as active but not yet transferred;
- displayed-functor fibre and transport plus displayed-transfor component
  families as active but staged for USABILITY-2A; and
- the desired whole displayed-functor laxity transfor as deliberately absent
  from the active authority, whose component-level cells do not authorize
  reconstructing it.

The ordinary bracket compiler's exact active but untransferred basis is
recorded separately from the frozen 24-owner base Core catalog:
`id_func`, `Const_func_func`, `sym_func_func`, `diag_func_func`,
`Product_cat`, both product projections, `Product_pair`,
`Product_map_func`, `Eval_func`, `comp_cat_fapp0`, `curry_func_func`, and
`uncurry_func_func`. This avoids accidental MVP/profile drift and gives
USABILITY-1C a direct typed-transfer list; no generic Lambdapi parser is
required.

The selector returns the exact ordinary semantic owners for object, one
arrow, and whole hom action. It fails closed with stable codes for missing
expected shape, classifier mismatch, untransferred section action, displayed
action, the absent whole laxity owner, and reserved ordinary naturality. The
frozen diagnostic contract additionally covers abstraction-layer ambiguity,
object-only arrow use, polarity mismatch, and a missing bracket structural
owner.

Only `:^n` remains canonical source notation. `functorial` and `object-only`
are stable internal TypeScript variation names; this row does not standardize

## USABILITY-1B Completion Record

USABILITY-1B adds the root-only `CoreCategoricalScopedBuilder` and immutable
contextual IR in `src/v3_2/categorical_surface.ts`. It does not add a Core
owner or an operation-specific checking path. Instead,
`elaborateSurfaceOperationFromOperands()` exposes the existing declarative
surface-operation interpreter at an already-typed operand boundary; both the
older direct surface and the categorical frontend reuse the same telescope,
constraint, recovered-slot, result-classifier, and provenance data.

The first supported direct TypeScript abstraction is:

```ts
const h = builder.categoricalLambda(
  "u",
  A,
  B,
  u => builder.apply(F, u)
);
```

The callback executes exactly once and is not stored. Its opaque slot token is
reified into immutable first-order evidence:

```text
typed-application functor.object
  subject = explicit-core-term F
  argument = slot-reference 0
```

The eta bracket rule then compiles `h` to the existing explicit Core term
`F : Functor(A,B)`. Applying `h` afterward uses the same frozen USABILITY-1A
selector and declarative owner schemas:

```text
h x                 -> functor-object(F,x)
h f                 -> functor-hom-capped(F,f)
wholeAction(h,x,y)  -> functor-hom-full(F,x,y)
```

The whole-action API is a typed Hom-boundary request, not a concrete arrow
term. A full transfor-style evaluator can therefore never be obtained by
